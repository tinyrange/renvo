Replacement plan

Renvo Native Backend Scalability Plan

Replace large, independently maintained native backend implementations with a compact, systematic description of their differences—without forcing Wasm into a native-machine model, inventing a second programming language, or weakening Renvo's compiler performance gates.

This document supersedes the earlier universal machine-definition plan. It incorporates the architecture meeting conclusions and describes the implementation sequence from the current branch to the intended system.

1. Corrected problem statement

The reason to introduce machine definitions is not primarily to remove the word “Go” from the repository, nor to make built-in and custom backends share a code path for its own sake. The problem is that the current backend implementation strategy does not scale to the number of architectures Renvo intends to support.

Today, each architecture tends to accumulate a large Go implementation containing instruction emission, semantic lowering, ABI rules, runtime behavior, relocations, and output-format construction. This is difficult to maintain and difficult to refactor because the compiler operates under unusually strict limits:

  • the constrained Renvo compiler artifacts must remain inside their existing gates;
  • compiler peak memory and writable reservation are bounded;
  • compiler CPU time and deterministic VM steps are bounded;
  • generated application binaries have hard size limits;
  • fixed-target builds must not retain unrelated backends;
  • self-hosting must remain viable under the same constraints.

Four native architecture families are currently in production: amd64, 386, ARM, and AArch64. Supporting another six, twenty, or thirty architectures by copying the existing backend shape is not sustainable. The system needs a compact way to describe only the differences that matter while compiling those descriptions into the direct, efficient code required by the existing gates.

Primary design question: What is the minimum authored description needed to express the real differences among native architectures and their ABI/OS combinations, while compiling to code that is at least as small and fast as the current specialized backends?

What the current experiment taught us

  • Moving a large Go backend verbatim into a go backend block changes source ownership but does not improve scalability.
  • A universal contract that treats native machines, Wasm, and VM bytecode as equivalent creates adapters and special cases instead of reuse.
  • Generated Go is useful when it is the compact result of systematic input; it is not useful when it is another full copy of hand-maintained backend code.
  • Embedded Go remains a valuable escape hatch, but it must not be the default place where the whole backend lives.
  • We do not need—and will not build—a static analyzer that judges whether an embedded Go function is “too complicated.”

2. Desired outcome and definition of success

Renvo will have an explicit native-backend family whose definitions describe machine facts, instruction families, operation selection, ABI rules, runtime composition, relocations, and image-format parameters. Generation will specialize those declarations into direct Go functions and constants. Irregular algorithms may be supplied through named, signature-checked Go hooks.

The built-in native definition set will describe amd64, 386, ARM, and AArch64 while writing shared native, ABI, runtime, and format behavior once. The generator will emit independently prunable target implementations. Wasm and VM32 will remain a separate backend family and will not be used to distort the native schema.

Definition of done

  1. The production native backends for amd64, 386, ARM, and AArch64 are generated from the new native schema.
  2. Adding a native architecture requires describing its machine and ABI differences, not copying Linux, Windows, ELF, PE, frame, and generic semantic-lowering implementations.
  3. Shared OS/runtime and output-format behavior is represented once in the built-in native definition set and specialized with explicit machine parameters.
  4. Generated fixed-target compilers contain only the selected architecture, ABI, runtime, relocation, and format composition.
  5. The architecture-specific Go remaining in native definitions is limited to named irregular algorithms reached from typed schema hooks. No complexity analysis of those functions is performed.
  6. A schema-only 8086 exercise and AVR exercise demonstrate that the model does not silently assume 32/64-bit flat memory, symmetric registers, one address space, or regular instruction encodings.
  7. Wasm and VM32 continue to pass their full tests through their bespoke backend family, without pretending to implement the native contract.
  8. The deduplicated native source set contains at most 60,000 semantic bytes and 200 declarations of embedded Go, enforced without weakening a compiler performance gate or moving target logic into an unmeasured file.
  9. Built-in and custom native definitions use the same schema, resolver, validator, hook checker, reachability rules, and direct-code generator. Their packaging may remain different where checked-in specialization is measurably smaller or faster than the preparation bridge.
  10. Superseded per-architecture definition files, hand-maintained generated projections, and duplicate format/runtime algorithms are deleted. A bounded preparation adapter is not considered a second backend when it contains no machine semantics.
  11. No constraint in backend/main_test.go is loosened. The full backend suite, full frontend suite, and full self-hosting suite pass.

How scalability will be measured

The plan will report, but will not initially reject based on, these source metrics:

  • declarative lines per architecture and per target composition;
  • embedded Go lines, functions, and hook sites per architecture;
  • copied runtime/format algorithms across definitions;
  • generated source and compiled text added by one architecture;
  • fixed-target pruning results;
  • compiler steps, wall time, peak RSS, and output size.

These are engineering feedback, not a Go complexity policy. The hard acceptance criteria remain the existing executable tests and performance gates. The size of binaries produced by the host Go toolchain is not an acceptance metric; those builds are development and packaging machinery, not the constrained Renvo output being optimized here.

3. Scope and explicit boundaries

In scope

  • amd64, 386, ARM, and AArch64 native backends;
  • Linux, Windows, Darwin, and Linux-kernel compositions currently supported;
  • ELF, PE/COFF, Mach-O, and relocatable native output already in production;
  • native ABI, runtime, relocation, and image reuse;
  • checked-in generated source for normal Go modules;
  • custom native definitions and prepared artifacts;
  • fixed-target pruning and self-hosting;
  • 8086 and AVR schema stress fixtures.

Out of scope

  • shipping an 8086 or AVR product backend in this effort;
  • embedded-board runtime or board-description work;
  • forcing Wasm or VM32 through native instruction/ABI abstractions;
  • a macro system or general rewrite language;
  • interpreting instruction recipes while compiling user programs;
  • proving termination or complexity of embedded Go;
  • loosening compiler or generated-binary gates;
  • adding excluded frontend features such as goroutines or generics.

Existing requirements retained

  • Built-in generated backends are checked into the repository and compile in ordinary Go-module builds.
  • A distributable custom machine definition remains one closed import graph rooted at an explicitly selected file. Every import is relative to its importer; there is no ambient definition search path.
  • Each built-in native target is one closed import graph rooted at its <os>_<arch>.rtg entrypoint. Shared ISA and format fragments keep reusable code coherent, and generation emits separate prunable outputs.
  • Embedded Go is parsed and type-checked with Renvo's existing frontend, contributes to the definition hash, and is emitted as ordinary source.
  • Custom backend preparation invokes Renvo, not the host Go toolchain.
  • The selected target and definition identity remain bound into RTGU.
Splitting built-ins into target entrypoints does not make the generated compiler universal. The generator must still emit only declarations reachable from the selected target for fixed-target builds.

4. Non-negotiable design principles

  1. Optimize marginal architecture cost. The important number is the new authored and compiled code required by the next native architecture, not whether the repository contains Go.
  2. Describe recurring structure; program irregular behavior. Tables and typed declarations own facts and bounded selection. Go owns algorithms that are clearer as code.
  3. Strong by construction, not clever analysis. A hook is narrow because the schema gives it a narrow signature and purpose. The compiler does not inspect its loops, branches, or size.
  4. Compile composition away. Target selection, widths, ABI, runtime, relocation, and format choices become constants and direct calls. No definition AST or string property lookup remains in the generated code path.
  5. Keep backend families honest. Native machines share a native contract. Wasm/VM use a structured backend contract. A family can share the frontend unit without sharing false machine abstractions.
  6. One owner for each reusable behavior. Linux process setup, PE layout, or ELF section construction is not copied into every architecture. Machine-specific parameters and relocations remain explicit.
  7. No hidden architecture backend. Shared native libraries may implement format-neutral and format-specific reusable mechanics, but they may not contain an undeclared x86, ARM, or vendor-specific encoder.
  8. Performance gates are design inputs. Generation is accepted only when compiler size, time, memory, and output quality remain inside the existing limits.
  9. Migration deletes code. A generated native path is not complete while an equivalent hand-authored machine implementation remains as a fallback. Packaging adapters may remain when they preserve a hard gate and contain no architecture policy.

5. Backend family boundary

The frontend produces one canonical linked unit, but code generation may be implemented by different backend families.

       object, or module                  or RNVM bytecode

native_v1

This effort defines and migrates native_v1. It assumes a machine with named storage locations, explicit instruction emission, relocatable code/data, an ABI, and an image/object composition. It must support word widths below 32 and multiple address spaces at the schema level, even though the first production migrations are 32/64-bit flat machines.

Wasm and VM32

Wasm has structured control flow, module construction, index spaces, and validation rules unlike a native ISA. VM32 is close enough to share some of that lowering, but neither should force native concepts such as physical registers, call-clobber sets, executable relocations, or native image sections.

  • The current Wasm/VM implementation remains operational.
  • Native generator code does not import Wasm-specific decisions.
  • Shared frontend semantics stay above the family boundary.
  • If the structured family receives its own declarative schema later, it is designed from Wasm/VM requirements rather than copied from native_v1.
  • Existing Wasm and VM size/runtime gate allowances remain exactly as currently defined.

6. Minimum native description model

The native schema is split into layers because each layer varies at a different rate. The generator resolves them once and emits a fixed composition.

6.1 Machine model

The machine declaration owns:

  • integer and native word widths;
  • data, code, and function pointer widths;
  • endianness and alignment limits;
  • named address spaces and pointer representation;
  • registers and register classes;
  • special roles such as stack, frame, primary, scratch, and syscall number;
  • condition representation;
  • legal scale, displacement, and immediate classes;
  • instruction alignment and byte order.

Register roles are mappings, not hard-coded names. A role may be absent when a target's declared lowering does not require it. The schema must not assume that all registers are interchangeable or that all pointer values inhabit one address space.

6.2 Operand and encoding forms

A form describes recurring instruction structure. It is intentionally bounded: named operands, constraints, fixed fields, and one encoder strategy. Examples include:

  • fixed byte or word sequences;
  • opcode plus register field;
  • register/register and register/immediate forms;
  • memory address encodings;
  • PC-relative branches with declared range and relocation;
  • multiword immediate construction;
  • conditional opcode families.

A common declarative form may be instantiated many times. An irregular form names a typed Go encoder hook. The form still declares its operands, output alignment, relocation behavior, and selection constraints so the surrounding structure remains visible.

6.3 Instruction families

Instructions are data rows over forms. Repeated width or condition variants are expressed as bounded tables, not copied functions. 

form rr(opcode bits, width bits) {
    operands = [destination: reg(gpr), source: reg(gpr)]
    encode = go nativeX86RR
}

instructions {
    move64     = rr(opcode = 0x89, width = 64)
    add64      = rr(opcode = 0x01, width = 64)
    subtract64 = rr(opcode = 0x29, width = 64)
}

The example is illustrative. The final grammar must remain smaller than the implementation it replaces and must not grow user-defined macros or arbitrary compile-time evaluation.

6.4 Native operation selection

The stable native operation contract describes what shared semantic lowering asks the machine to do. A binding selects:

  • one instruction row;
  • one bounded choice among rows based on declared operand classes;
  • one named Go lowering hook for an irregular multi-instruction algorithm;
  • an explicit unsupported result where the contract permits it.

Selection compiles to direct conditionals and calls. There is no general expression rewrite engine and no runtime search through recipes. 

bind native_v1 {
    move            = instruction move_native
    load.native     = choose load_by_address_class
    move_immediate  = go synthesizeImmediate
    signed_divide   = go lowerSignedDivide
}

6.5 ABI model

The ABI declaration owns:

  • argument and result register sequences by value class;
  • stack argument order and slot size;
  • stack and call-site alignment;
  • callee-saved and caller-clobbered sets;
  • hidden-result and aggregate return policy;
  • frame record and return-address policy;
  • variadic and external-call differences where supported;
  • typed hooks for genuinely irregular entry, call, or return sequences.

The shared native lowering generates ordinary frame, parameter, call, and return code from these facts. It does not contain an architecture name switch.

6.6 Runtime composition

Runtime declarations separate OS behavior from machine mechanics. A hosted runtime describes:

  • supported operations;
  • syscall or import identity;
  • argument/result placement through ABI roles;
  • entry-state and process-argument layout;
  • exit behavior;
  • static and dynamic import requirements;
  • small typed hooks for OS-specific algorithms.

Linux runtime behavior is written once, with architecture-specific syscall numbers and trap instruction supplied as data. Windows import and handle behavior is written once, with ABI and PE-machine parameters selected by composition. Darwin runtime behavior is similarly separated from the AArch64 encoder.

6.7 Relocations and output formats

Format declarations own reusable ELF, PE/COFF, Mach-O, and relocatable layout behavior within reusable native fragments. Architecture declarations supply:

  • machine identifiers;
  • class, endianness, and address width;
  • relocation kind mappings;
  • instruction-specific patch functions;
  • entry alignment and section flags;
  • architecture-specific import thunk requirements.

The common format implementation is not copied into each architecture. It operates on typed sections, symbols, and relocations and calls the selected machine's declared patch hook where the file format cannot resolve a relocation generically.

The implemented bounded encodings cover little-endian relative-32 labels, AArch64 and ARM32 label fields, relative-32 executable addresses, AArch64 page-plus-offset addresses, ARM32 split move addresses, PE relative addresses, and PE absolute addresses. ELF and PE executables and Linux-module ELF objects are selected by format kind and specialized from machine, width, alignment, image-base, section, relocation, and typed record-helper facts. Only the ARM split-immediate writer remains a narrow format hook.

6.8 Target composition

A target selects one compatible value for each axis:

target linux/amd64 {
    family       = native_v1
    machine      = x86_64
    abi          = sysv_x86_64
    runtime      = linux_hosted
    format       = elf_executable
    relocations  = elf_x86_64
    frontend     = go_amd64
}

Resolution checks widths, address spaces, endianness, ABI register classes, runtime requirements, relocation coverage, and output-format compatibility. Generation specializes the target and discards unrelated compositions.

7. Embedded Go boundary

Embedded Go is an opaque implementation language behind typed extension points. Renvo parses and type-checks it because generated code must compile, but it does not attempt to determine whether the function is simple, bounded, elegant, or terminating.

Allowed hook categories

Category Typical responsibility What remains declarative
Encoder ModRM/SIB, ARM rotated immediate, AArch64 logical immediate operands, constraints, instruction identity, effects
Lowering division sequence, long immediate synthesis, branch relaxation operation binding, required roles, clobbers, capability
Relocation patch a machine-specific split or scaled field relocation kind, width, range, addend policy
ABI edge unusual aggregate return or platform thunk register classes, stack policy, declared hook site
Runtime edge Windows command-line parsing or kernel metadata operation surface, imports, capabilities, selected target
Format edge architecture-specific import veneer or metadata patch sections, layout facts, format and relocation composition

Structural restrictions

  • Hooks are package-level declarations in the Renvo-supported Go subset.
  • Imports, package clauses, directives, and unsafe host escape are rejected.
  • Each hook is referenced from a typed declaration with a fixed signature.
  • Generated names are resolved through the parsed Go AST, not string substitution.
  • Only declarations reachable from the selected target are emitted.
  • The complete hook syntax contributes to canonical definition identity.
  • Straight-line calls and value plumbing use bounded sequence declarations; sequences have no branch or loop syntax and are not a second general-purpose IR.
There is no hook line limit, loop limit, cyclomatic-complexity check, or termination proof. The type boundary provides the compiler-enforced hook scope. Separately, the deduplicated native source set has a deliberately simple 60,000-semantic-byte and 200-declaration ceiling; this measures growth without attempting Go complexity analysis.

Hook review rule

A reviewer should be able to answer “why is this not a table or an existing form?” A hook is justified when the algorithm has real control flow or state that would make a declarative encoding less clear. This is a review convention, not language semantics.

8. Source authority and generation topology

The built-in native source of truth is a set of independent target entrypoints under backend/definitions/. Each entrypoint imports only the reusable ISA and format fragments it needs; Wasm and VM source remains in its separate entrypoint. 

backend/definitions/
    |
    +-- x86_64.rtg, x86_32.rtg
    +-- aarch64.rtg, arm.rtg
    +-- elf_amd64.rtg
    |
    +-- linux_amd64.rtg       -- @import "elf_amd64.rtg"
    +-- windows_amd64.rtg     -- @import "x86_64.rtg"
    +-- linux_kernel_amd64.rtg
    +-- linux_386.rtg, windows_386.rtg
    +-- linux_aarch64.rtg, darwin_aarch64.rtg
    +-- windows_aarch64.rtg, linux_arm.rtg
    |
    v
entrypoint resolution and reachability
    |
    +-- generated native kernel
    +-- generated architecture implementations
    +-- generated target descriptors
    +-- generated fixed-target source manifests
    +-- generated ordinary-Go built-in package

@import "relative/path.rtg" is a top-level composition directive. Resolution is relative to the importing file, imports may be nested, cycles are rejected, and diagnostics map back to the owning fragment. Each file is also a virtual package whose name is derived from its basename. Embedded Go declarations and bounded sequences use short names within that package; lowering adds a collision-proof internal qualification automatically. A target can add bounded sequences with extend arch; that block inherits the imported ISA's symbols, so its code uses short names without hand-written architecture prefixes. An explicit reference such as x86_64.encode remains available when ambiguity requires it. Machine identities, target names, and explicit export names remain definition-global. Directories and import spelling do not affect identity, but a virtual package basename is semantic because it participates in helper resolution.

One authoritative production projection

The current split between algorithm-only generated files and separate contract-only generated files will be removed. Each generated architecture production file contains the facts, algorithms, and direct operation bindings actually compiled by the backend.

  • No checked-in generated contract exists solely for tests.
  • Tests may generate temporary projections for golden inspection.
  • Every checked-in generated Go file is part of a documented build topology.
  • Stale-output tests regenerate the exact production artifacts.

Catalog identity versus target identity

A scalable multi-architecture catalog needs two deterministic identities:

  • Catalog identity hashes the complete closed source file and records exactly which authored catalog produced the release.
  • Target semantic identity hashes the selected target and the transitive declarations and embedded Go reachable from it, together with the native contract and generator compatibility versions.

RTGU bindings, target descriptors, and prepared-cache identity use the target semantic identity. Generated manifests additionally record the catalog identity for provenance. Adding an unrelated architecture to the catalog therefore does not invalidate existing targets, while changing shared runtime, format, ABI, or machine behavior changes every target that actually reaches it.

Reachability and hashing use resolved typed declarations, not source-text substring selection. Declaration order, comments, and formatting do not affect either identity.

Built-in and custom native outputs

The same resolver and generator have two output modes:

  • Built-in catalog mode: emit all production native architectures as separately prunable checked-in Go.
  • Fixed custom mode: emit one selected custom native target and compile it with the built-in host bootstrap.

Both modes use the same typed declarations and generation primitives. Built-ins project stable compiler-facing symbols so ordinary Go builds and fixed-target pruning stay fast. Custom targets project the same bindings through a target-neutral preparation adapter because their symbols cannot be known by the release compiler. The adapter is transport: it owns no instruction, ABI, runtime, relocation, or format semantics.

Compiler package duplication

The current ordinary-Go bundle copies the backend compiler into internal/backendcompiled/compiler_generated.go and carries a compressed source copy for preparation. This is not the first migration target because package refactoring can disturb performance independently of the schema.

After the native schema is authoritative, prototype one of:

  1. an importable target-neutral compiler kernel with generated native components; or
  2. a precompiled kernel plus generated component linking for prepared backends.

Adopt the prototype only if it reduces repository/runtime duplication without violating fixed-target size, memory, or self-host constraints.

9. Schema stress tests: 8086 and AVR

8086 and AVR are design fixtures, not production deliverables. Their job is to expose assumptions before the native schema becomes expensive to change.

8086 fixture

The 8086 exercise must represent:

  • 16-bit native words;
  • segmented code and data addressing;
  • non-uniform register roles and partial-register constraints;
  • small displacement and immediate forms;
  • near versus far control transfer;
  • stack and pointer representation that are not interchangeable;
  • a minimal ABI composition without claiming a shipping DOS runtime.

AVR fixture

The AVR exercise must represent:

  • 8-bit registers and multi-register values;
  • Harvard code/data address spaces;
  • asymmetric register constraints;
  • instruction pairs and limited immediate destinations;
  • small branch ranges and relaxation needs;
  • pointer register pairs;
  • a minimal call ABI without adding board or firmware policy.

Required fixture depth

Each fixture must parse, resolve, validate, generate compilable direct Go, and cover representative move, load/store, arithmetic, branch, call, and relocation operations. It need not compile the frontend or produce a bootable artifact.

Stress-test exit condition: the fixtures require no architecture-name conditionals in the generator and no generic macro/evaluation feature. If a required concept is absent, add the smallest typed schema concept that also improves or clarifies a production architecture.

10. Implementation phases

Implementation status: Phases 0 through 10 are implemented in the checked-in native definitions, generator, prepared-backend path, and production projections. Phase 11 was treated as a measured packaging optimization; the existing compressed source boundary remains because no replacement demonstrated a size/time/memory win. The steps below remain the acceptance trail for future architecture work.

Phase 0: Freeze evidence and inventory differences

  1. Record current backend performance results without modifying backend/main_test.go.
  2. Record fixed and universal compiler sizes, frontend compile time, deterministic VM steps, RSS, writable reservation, self-host time, and output sizes.
  3. Classify current native code by machine encoding, operation selection, ABI, runtime, relocation, format, and target composition.
  4. Identify byte-identical or structurally duplicated ELF, PE, runtime, frame, call, and relocation behavior.
  5. Preserve representative output goldens and minimal backend regression programs for every migrated behavior.
Exit: every proposed shared declaration is backed by existing repeated code or an explicit future-architecture requirement. No schema feature is added merely because it may be useful.

Phase 1: Establish backend families

  1. Introduce an explicit family field in target descriptors.
  2. Define native_v1 independently of Wasm/VM lowering.
  3. Keep the current Wasm/VM implementation behind a structured-family selection without changing its production algorithms.
  4. Remove native validation assumptions from the generic target descriptor layer.
  5. Add tests proving each advertised target selects exactly one backend family and carries compatible frontend facts.
Exit: Wasm/VM behavior is unchanged, while native schema work can proceed without accommodating structured-control or module-index semantics.

Phase 2: Build the minimum native schema

  1. Implement machine facts, register classes, roles, and address spaces.
  2. Implement bounded operand, encoding-form, and instruction tables.
  3. Implement typed operation bindings and explicit rejection.
  4. Implement ABI sequences, stack policy, save sets, and typed ABI hooks.
  5. Implement runtime composition and syscall/import fact tables.
  6. Implement format parameters and machine relocation hooks.
  7. Emit direct Go functions and constants with deterministic naming.
  8. Emit per-target review metrics for declarative and Go source volume.
  9. Enforce the deduplicated production native source set at no more than 60,000 semantic Go bytes and 200 Go declarations.
Exit: a small synthetic native machine can generate, compile through host Go and Renvo, and emit direct calls with no runtime definition interpreter.

Phase 3: Stress the schema before production migration

  1. Add the 8086 schema fixture.
  2. Add the AVR schema fixture.
  3. Review every schema addition requested by a fixture against the four production native machines.
  4. Reject fixture-driven generality that would require macros, arbitrary evaluation, or a second IR.
  5. Document concepts deliberately deferred to a future native_v2.
Exit: 8086 and AVR representative definitions generate valid direct source, and the schema remains bounded and readable.

Phase 4: amd64 vertical slice

amd64 is the first production proof because it exercises the common host, strict performance gates, two hosted OSes, object output, static imports, and Linux kernel-module output.

  1. Move x86-64 instruction families and constraints into declarative forms.
  2. Keep ModRM/SIB, relaxation, and unusual immediate algorithms as typed Go hooks.
  3. Generate SysV and Windows ABI mechanics from declarations.
  4. Compose Linux, Windows, and kernel runtime behavior from shared components.
  5. Compose ELF, PE/COFF, and relocatable ELF output from shared formats.
  6. Route one test-only amd64 compiler through the generated native contract while the production path remains available for equivalence.
  7. Compare code bytes, relocations, symbols, object files, executables, kernel modules, runtime behavior, and all performance measurements.
Exit: generated amd64 covers the full current amd64 scope, passes all amd64 tests, and remains inside unchanged performance gates.

Phase 5: Make generated amd64 authoritative

  1. Switch built-in amd64 targets to the generated native path.
  2. Remove the old amd64 production dispatch and duplicated algorithms.
  3. Generate one authoritative amd64 production file.
  4. Verify fixed-target pruning for Linux, Windows, and kernel compositions.
  5. Rerun the full backend suite after deletion, not only before it.
Exit: no amd64 fallback or parallel encoder can produce a release artifact.

Phase 6: Add 386 and prove x86 sharing

  1. Reuse x86 forms where the encoding structure is actually shared.
  2. Describe 32-bit registers, operand defaults, addressing, and ABI differences.
  3. Reuse Linux and Windows runtime behavior with 386 syscall/import facts.
  4. Reuse ELF and PE format algorithms with 32-bit parameters and relocations.
  5. Preserve 386-specific hooks only where encoding or ABI behavior differs.
  6. Delete the legacy 386 production path after full equivalence.
Exit: adding 386 does not copy OS/runtime/format implementations, and both Linux/386 and Windows/386 pass all gates.

Phase 7: Add AArch64 and ARM

  1. Describe fixed-width instruction families and immediate constraints.
  2. Keep AArch64 and ARM immediate synthesis as typed hooks where appropriate.
  3. Generate AAPCS32, AAPCS64, and Windows ARM64 ABI mechanics.
  4. Reuse Linux runtime and ELF format behavior while supplying machine identifiers, syscall facts, and relocations.
  5. Reuse Windows runtime and PE behavior for ARM64 without copying Windows process/import code.
  6. Reuse Mach-O behavior for Darwin/ARM64 with AArch64 relocations.
  7. Delete legacy ARM and AArch64 production paths after equivalence.
Exit: all four current native architectures use the generated native contract, and every existing native target passes.

Phase 8: Split built-ins into target entrypoints

  1. Make every target-named file under backend/definitions/ an independent root that imports one reusable fragment per required ISA or shared format.
  2. Keep machine facts, encoders, and reusable calling conventions in the ISA fragment. Keep each unique ABI, runtime, executable/object format, entry sequence, hook, and final target declaration in a target-named entrypoint such as darwin_aarch64.rtg. Use extend arch to inherit short ISA helper names automatically.
  3. Generate separate production files and manifests by target reachability.
  4. Generate completeness documentation showing which declarations each target retains.
  5. Ensure each closed entrypoint hash and target-specific semantic identity remains deterministic.
  6. Verify adding an unreachable fixture architecture leaves all existing target semantic identities unchanged.
Exit: shared behavior is authored once, while a fixed target does not pay for unrelated catalog contents.

Phase 9: Converge custom native backends

  1. Make custom native definitions declare family = native_v1.
  2. Use the same resolver, validator, hook checker, and generator as built-ins.
  3. Emit the same target-specialized native semantics as catalog mode.
  4. Replace exact source-spelling specialization with explicit typed generation configuration.
  5. Preserve RTGU target/hash/version binding and RTGB compatibility checks.
  6. Run a custom target unknown to the release compiler end to end.
Exit: a built-in native target and an equivalent external definition resolve the same declarations and operation bindings; only packaging, stable symbol projection, and selected identity differ.

Phase 10: Delete duplicate semantic topology

  1. Remove separate contract-only generated files.
  2. Remove old hand-authored architecture source after its generated projection is authoritative.
  3. Remove preparation-time source-spelling rewrites in favor of typed generation settings.
  4. Keep the preparation adapter target-neutral and free of machine semantics.
  5. Do not force built-ins through the preparation bridge merely to make packaging look uniform; retain direct checked-in calls when the bridge would consume compiler time, source, or binary-size budget.
Exit: built-in and custom targets derive machine behavior from generated compositions. Any remaining topology difference is a measured transport boundary, not a parallel backend implementation.

Phase 11: Reduce compiler transport duplication

  1. Measure the ordinary-Go copied compiler and compressed preparation source separately.
  2. Prototype an importable kernel or precompiled component boundary.
  3. Test fixed-target pruning and self-host output for the prototype.
  4. Adopt it only if all existing size, time, and memory gates pass.
  5. Delete generated copies made unnecessary by the accepted topology.
Exit: the chosen topology carries the minimum compiler representation required for ordinary builds and custom preparation.

Phase 12: Final cleanup and documentation

  1. Update backend author documentation around the native layers and hook boundary.
  2. Document how to add one native architecture without editing shared generator switches.
  3. Document Wasm/VM as a separate backend family.
  4. Regenerate all checked-in outputs and require a clean worktree.
  5. Run the final acceptance suite under an explicit memory cap.

11. Testing strategy

Language and schema tests

  • scanner/parser coverage for every native declaration;
  • duplicate, missing, and unknown-field diagnostics;
  • register-class and role compatibility;
  • address-space and pointer-width compatibility;
  • instruction operand and constraint validation;
  • complete native operation bindings or explicit rejection;
  • ABI register, stack, and save-set validation;
  • runtime operation and import/syscall validation;
  • relocation and format compatibility;
  • embedded Go signature and reachability tests;
  • canonicalization and deterministic generation;
  • resource-limit rejection for hostile or malformed definitions.

Generated-source tests

  • generate twice and require byte-identical output;
  • compile generated source through host Go and Renvo;
  • verify fixed-target output contains no unrelated target symbols;
  • verify one authoritative production projection per architecture;
  • verify checked-in generated output is current;
  • report declarative and embedded Go metrics without rejecting complexity.

Backend equivalence

  • instruction boundary tests for every form and constraint edge;
  • relocation range, addend, and patch tests;
  • ABI calls, returns, aggregates, stack arguments, and static calls;
  • runtime operation behavior and unsupported diagnostics;
  • executable and object layout comparisons;
  • Linux, Windows, Darwin, kernel-module, and cross-target execution tests;
  • self-host compiler output and self-hosted application compilation;
  • minimal regression programs under backend/tests/ for every discovered miscompilation.

Family isolation

  • native schema changes run the full Wasm/VM regression suite;
  • Wasm/VM source contains no dependency on native register or relocation models;
  • frontend unit binding works identically across families;
  • family mismatch is rejected before code generation.

Custom workflow

  • unknown native target preparation;
  • explicit -t authority with multi-target definitions;
  • cache miss, cache hit, concurrent publication, and corrupt entry recovery;
  • RTGB round trip and compatibility rejection;
  • wrong definition, descriptor version, host, or target binding rejection;
  • process runner and injectable runner behavior;
  • closed definition preparation without a repository checkout or host Go.

12. Performance and resource plan

Existing limits in backend/main_test.go are immutable for this effort. A generated path must fit the current gates; the gates are not adjusted to accommodate the design.

Measurements at every production phase

Measurement Why it matters Required comparison
Fixed-target compiler size Detect retained schema/catalog code and unrelated targets baseline and hard gate
Universal compiler size Measure marginal cost of each architecture before/after each migration
Generated application size Protect code quality and output constraints goldens and hard gate

Generation performance rules

  • generation occurs ahead of user-program code generation;
  • fixed generated code contains direct calls and constants;
  • no runtime schema traversal or instruction recipe interpreter;
  • reachability starts from one selected target for fixed output;
  • unused hooks and declarations are not emitted;
  • table specialization must not explode binary size through blind Cartesian expansion;
  • specialize only variants that remove meaningful runtime work or simplify generated code.

Safe local execution

Expensive tests should run with systemd-run --user --scope and explicit memory limits to avoid taking down the working session. CPU affinity may be used where existing calibrated performance tests require a stable core class, without changing the test thresholds. 

systemd-run --user --scope \
  -p MemoryMax=4G \
  -p MemorySwapMax=0 \
  go test ./backend -count=1 -timeout=45m

systemd-run --user --scope \
  -p MemoryMax=4G \
  -p MemorySwapMax=0 \
  go test ./frontend_tests -count=1 -timeout=45m

13. Migration discipline and pull-request sequence

Each pull request must have one reviewable architectural claim and must leave production behavior unambiguous.

  1. Backend family boundary with no production algorithm changes.
  2. Minimum native schema and synthetic generated compiler.
  3. 8086/AVR stress fixtures and schema corrections.
  4. Complete test-only amd64 vertical slice.
  5. Authoritative amd64 switch and legacy deletion.
  6. 386 migration and shared x86/runtime/format proof.
  7. AArch64 and ARM migration.
  8. Independent built-in native entrypoints and target-rooted reachability.
  9. Custom native preparation convergence.
  10. Dual-topology and inactive-stub deletion.
  11. Optional compiler-kernel/package duplication reduction.
  12. Final documentation, generation audit, and acceptance run.

Rules for every migration PR

  • Do not modify performance constraints.
  • Do not retain a production fallback after the generated path is authoritative.
  • Do not hardcode tests or prebuild output.
  • Add minimal regressions for discovered miscompilations.
  • Run relevant focused tests before the full suite.
  • Record generated source, compiler size, steps, memory, and output deltas.
  • Regenerate checked-in output and require git diff --check.
  • Keep unrelated user worktree changes untouched.

Deletion ledger

The implementation should maintain a small ledger showing which current files or branches disappear at each phase. Expected deletion targets include:

  • separate contract-only generated architecture files;
  • hand-maintained architecture algorithms superseded by generated projections;
  • source-spelling preparation rewrites;
  • duplicated per-architecture runtime and format algorithms;
  • superseded per-architecture built-in definition files;
  • copied compiler representations made unnecessary by an accepted kernel topology.

14. Risks and controls

Risk Control
The schema becomes another programming language. Only bounded facts, tables, and choices; use typed Go for control flow.
Embedded Go again becomes the entire backend. Require every hook to occupy a typed schema site; enforce the deduplicated native-source ceiling; report per-target metrics; review why a hook is necessary; reject moving target logic into an unmeasured file.
The compiler grows a Go complexity analyzer. Explicitly prohibit complexity and termination analysis; type-check signatures only.
Wasm requirements distort native abstractions. Separate backend families and regression-test family isolation.
Shared format/runtime code becomes a hidden architecture backend. Keep machine identifiers, instruction patches, relocations, and irregular hooks in explicit machine declarations.
A shared native source set bloats fixed compilers. Target-rooted reachability, generated pruning tests, and existing size gates.
Table specialization explodes generated source. Measure each family; specialize only useful variants; allow direct compact selection where smaller.
8086/AVR overgeneralize the first version. Add only concepts that clarify a production architecture or are fundamental machine facts; defer the rest.
Built-in and custom behavior diverge. Converge on the same resolver and generator after the native model is proven; run equivalent-definition tests.
Package refactoring destabilizes performance. Keep compiler transport cleanup after semantic migration and adopt only after measured proof.
Generated code is technically correct but unreviewable. Stable names, compact headers, source mapping, one production projection, and small generated diffs.
Legacy paths linger indefinitely. Each architecture migration has a deletion exit condition and a full-suite run after deletion.

15. Final acceptance run

  1. Generate all checked-in native outputs twice and compare bytes.
  2. Regenerate target registry and machine-definition documentation.
  3. Require a clean generated-output diff.
  4. Run definition parser, validator, canonicalization, and generator tests.
  5. Run the 8086 and AVR schema stress fixtures.
  6. Run all native instruction, ABI, runtime, relocation, object, and executable tests.
  7. Run all custom definition, cache, RTGB, runner, and binding tests.
  8. Run the complete Wasm and VM32 suites unchanged.
  9. Run the full backend suite under a memory cap and unchanged performance requirements.
  10. Run the full frontend suite, including full self-hosting, under a memory cap.
  11. Build ordinary Go-module binaries for every supported host.
  12. Verify fixed-target binaries contain no unrelated native architectures.
  13. Verify remaining preparation adapters contain no machine semantics.
  14. Compile and run one custom native target unknown to the release registry.
  15. Verify the deduplicated native source set remains within 60,000 Go bytes and 200 declarations.
  16. Record final source, generated size, compiler size, steps, RSS, and output deltas.
Final success statement: A new native architecture can be added by describing its machine, instruction, ABI, and relocation differences plus a small number of typed algorithm hooks. Existing OS/runtime and format behavior is reused, generated code is direct and prunable, Wasm/VM remain honest bespoke backends, and every existing performance and self-hosting gate still passes.
