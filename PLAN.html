Microcontroller refactor and ESP32 USB stack

Turn the current example-local ESP32 code into a small, reusable device library built from structs implementing narrow interfaces, then build a controller-independent USB device stack above it. Validate each layer against tinyrange/renvo_emu before expanding the supported USB classes.

1. Target outcome

Microcontrollers

Applications import one hardware package as board, use attached devices directly—such as board.BlueLED.Set(true)—and pass typed board connectors to portable constructors such as i2c.New(board.Grove). Chip details remain behind those values.

USB

USB protocol and class logic is independent of the ESP32 controller. ESP32-S3 supplies a DWC2 device-controller implementation; ESP32-C6 retains its fixed USB Serial/JTAG console through a separate adapter.

Primary success measure: an application can select a board, compose one or more USB functions, compile with Renvo, enumerate in the emulator, and run unchanged on supported hardware without importing example-internal code.

3. Scope and boundaries

  • Keep MMIO addresses and register bit definitions in chip packages, board wiring in board packages, protocol behavior in portable packages, and target startup/ABI behavior in RTG targets.
  • Use ordinary Renvo-supported Go: concrete structs, small interfaces, slices and fixed arrays. Do not require generics, goroutines, channels, cgo, reflection, or an ESP-IDF dependency.
  • Use statically owned buffers with explicit capacities. No allocation or interface dispatch is required in an interrupt path.
  • Implement USB device mode first. USB host and OTG role switching are separate projects.
  • Preserve the existing print path and its bounded no-host behavior while migrating internals.
Hardware boundary: ESP32-C6 USB Serial/JTAG is a fixed-function peripheral and must not masquerade as the general USB device controller. The planned multi-class stack targets ESP32-S3 DWC2 first. Any later chip is admitted only after its controller satisfies the same low-level contract.

Every hardware package declares package board, so applications can swap the import path without rewriting selectors. Portable code never imports a board or concrete ESP controller. The board package is the composition root: it binds reusable chip objects to physical pins and exposes them as named devices or typed connector descriptions.

5. Board-first interface contracts

The public API begins with the board, not the MCU. Applications should not configure IO muxes, choose controller numbers, or translate pin constants for ordinary board features.

import (
    board "renvo.dev/device/board/m5nanoc6"
    "renvo.dev/device/i2c"
    "renvo.dev/device/sensor/sgp30"
)

func appMain(args []string) int {
    board.BlueLED.Set(true)

    bus := i2c.New(board.Grove)
    air := sgp30.New(bus)
    reading, err := air.Measure()
    // ...
}

5.1 Exported board values

A board exports two deliberately different kinds of value:

KindExamplesBehavior
Attached deviceboard.BlueLED, board.Button, board.RGB, board.DisplayReady to use. Board-specific polarity, pins, power gates and reset wiring are already encoded by the value.
Connector/portboard.Grove, board.HeaderSPI, board.USBA typed immutable description consumed by a portable constructor. It carries controller capability, pin routing, defaults and shared ownership state.

Board globals are concrete, addressable values. Methods that mutate hardware use pointer receivers internally, while normal calls retain the direct form board.BlueLED.Set(true). Attached-device methods perform idempotent lazy initialization on first use, so that call alone configures the IO mux, initial level and output enable safely; an application does not need a preceding ConfigureBlueLED call. Applications never receive raw GPIO numbers for an attached LED or button.

5.2 Narrow capabilities below the board

// package gpio
type Pin interface {
    Configure(Config) error
    Set(bool)
    Get() bool
}

// package i2c
type Controller interface {
    Configure(sda, scl gpio.Pin, frequency uint32) error
    Tx(address uint16, write, read []byte) error
}

type Port struct {
    // Constructed by board packages; details are intentionally not needed by apps.
}

func New(port Port) *Bus

// package clock
type Source interface {
    NowTicks() uint64
    TicksPerSecond() uint64
}

i2c.New returns a concrete bus bound to the controller and pins carried by the port. A board-provided port is valid by construction; transaction failures are returned from Tx. The same shape applies to spi.New(board.HeaderSPI) and usb.New(board.USB, ...).

5.3 Composition and ownership rules

  • Names describe the PCB: use BlueLED, Grove and Display when those names appear in board documentation. Do not make users rediscover GPIO7 or I2C0.
  • Devices are values: an active-low LED is a gpio.LED configured with polarity; a button is a gpio.Button configured with pull and active level. Their API is board-independent, initialization is idempotent, and the first ordinary operation makes the device ready.
  • Connectors are descriptions: board.Grove identifies its SDA/SCL pins, usable controller, default frequency and ownership token. It does not eagerly start the bus during package initialization.
  • Constructors choose policy: i2c.New turns an I²C port into a bus. Sensor constructors consume the small transaction interface, so sgp30.New(bus) is independent of board and chip.
  • One owner per controller: copied port values refer to shared controller state. Conflicting live configurations return a stable busy/configuration error rather than silently reprogramming hardware.
  • Time: expose a monotonic clock plus a polling delay helper. Frequency conversion lives with the clock implementation.
  • MMIO: typed register wrappers centralize volatile access and read/modify/write intent. Registers that are write-one-to-clear or set/clear aliases expose operations that prevent accidental generic RMW.
  • Errors: use a small stable set of sentinel errors—invalid configuration, busy, timeout, NAK, short transfer, disconnected—without formatted allocation in low-level code.
API rule: board-level selectors are concrete and ergonomic; interfaces appear at reusable driver seams. Hot loops and interrupt/poll handlers operate on concrete receivers so the generated code remains predictable.

6. USB stack architecture

6.1 Controller contract

The portable core consumes events and submits endpoint transfers. It does not read DWC2 registers.

type DeviceController interface {
    Start(DeviceConfig) error
    Connect() error
    Disconnect()
    Poll(*Event) bool
    ConfigureEndpoint(EndpointConfig) error
    SubmitIn(endpoint uint8, data []byte) error
    PrepareOut(endpoint uint8, data []byte) error
    Stall(endpoint uint8, in bool)
    SetAddress(address uint8)
}

Poll emits reset, suspend, resume, setup, IN-complete, OUT-complete and error events. Address application is delayed until the status stage completes. The controller owns FIFO/DMA mechanics; the core owns USB protocol state.

6.2 Portable device core

  • Explicit states: detached, default, addressed, configured and suspended.
  • A dedicated EP0 state machine handles setup, bounded data stages, status stages, cancellation on a new setup packet, stalls, and standard requests.
  • Descriptor writing is deterministic and capacity checked. Device, configuration, interface, endpoint, string, BOS and device-qualifier responses share one encoder.
  • A composite builder allocates interface numbers, string indexes and endpoint addresses once at startup, then freezes the descriptor graph.
  • Class/vendor requests route by recipient and interface ownership. Unknown or malformed requests stall EP0.
  • Device.Poll() drains a bounded number of controller events and class work per call so applications remain responsive without goroutines.

6.3 ESP32-S3 DWC2 driver

  1. Power and clock the internal PHY through the ESP USB wrapper; force device mode and validate the Synopsys core identity/configuration.
  2. Perform core reset and RX/TX FIFO sizing from the composed endpoint requirements.
  3. Implement EP0 receive status decoding, FIFO reads, FIFO-empty writes, transfer-complete handling and bus-reset recovery.
  4. Add non-control bulk, interrupt and isochronous endpoints incrementally. Keep ISR work to acknowledging/capturing state; protocol advancement occurs in Poll.
  5. Make timeouts and FIFO bounds explicit. A disconnected host or wedged endpoint must not block the whole application.

6.4 Fixed USB Serial/JTAG adapter

Move duplicated C6/S3 console mechanics behind a concrete writer/reader abstraction shared by target glue. It remains available for print and recovery logging even when S3 DWC2 runs a composite device. It is not registered as a DeviceController.

8. Emulator-first development with renvo_emu

The adjacent tinyrange/renvo_emu repository already contains the useful S3 substrate: USB wrapper state, a DWC2 device model, endpoint FIFOs and interrupts, and a scripted functional host. Use that as executable specification, not merely a smoke-test runner.

  1. Add tiny Renvo firmware fixtures that expose one behavior at a time: reset handling, each standard request, address timing, configuration, stall recovery, endpoint IN/OUT and composite routing.
  2. Extend the emulator host script only when a new observable host action is needed. Keep assertions at the USB transaction level rather than recognizing a particular firmware image.
  3. For every emulator-model gap uncovered by valid firmware, first add a focused emulator regression, then extend the model. Do not weaken firmware to accommodate an inaccurate model.
  4. Capture deterministic transfer traces for failures. Debug logging remains opt-in and tests compare structured outcomes, not log strings.
  5. Run the same application-level protocol vectors against a fake in-memory controller, the DWC2 emulator, and physical S3 hardware.

The C6 emulator continues testing the fixed Serial/JTAG adapter and board refactor. It is not used to claim support for arbitrary USB classes.

9. Single-PR delivery phases

All phases below are commits or reviewable checkpoints on one implementation branch and one PR. The branch remains draft while any phase is incomplete, and it becomes mergeable only after the final definition of done is satisfied.

Phase A — contracts and one vertical refactor

  • Add MMIO primitives and the minimal gpio, i2c, spi and clock capability interfaces.
  • Refactor M5NanoC6 GPIO/LED/button into concrete ESP32-C6 structs exported by package board.
  • Make board.BlueLED.Set(true) a complete, safe first operation with no hidden prerequisite call.
  • Keep compatibility wrappers temporarily so examples remain green.
  • Add frontend acceptance coverage for package globals, pointer-receiver calls, interface fields and the exact constructor patterns used by device packages.
Exit: a blink application consists of a board import plus board.BlueLED.Set(...); blink and button/RGB applications pass in renvo_emu and on the NanoC6; generated output contains real interface semantics, not special cases.

Phase B — buses, time and board migration

  • Move clocks, software/hardware I²C, SPI, RMT/RNG and board-attached device drivers behind the new seams.
  • Migrate M5StickS3 display and buttons without combining display policy with SPI/GDMA ownership.
  • Delete compatibility wrappers only after both example trees use the new packages.
Exit: current microcontroller examples import reusable packages; example-local code contains applications and wiring only.

Phase C — USB foundation

  • Add setup packet, descriptors, device states, EP0 and a fake controller test double.
  • Add the S3 DWC2 controller through reset, enumeration and vendor bulk loopback.
  • Extract the fixed Serial/JTAG adapter without changing print behavior.
Exit: S3 enumerates deterministically in renvo_emu and on hardware, passes malformed-request/stall/reset cases, and performs bidirectional bulk transfers.

Phase D — useful composite device

  • Implement CDC ACM, HID and WebUSB/vendor functions.
  • Prove endpoint/interface allocation with a CDC + HID + vendor composite configuration.
  • Add host-specific checks on Linux, macOS, Windows and a WebUSB-capable browser where applicable.
Exit: the composite firmware works without descriptor forks per operating system and survives reconnect, reset and repeated configuration.

Phase E — advanced classes

Deliver Mass Storage, MIDI, CDC Ethernet, Audio, MTP and ADB in the sequence above. Each receives its own protocol package, emulator host coverage, memory budget and hardware demonstration.

11. Risks and decisions to lock early

  • Frontend gaps: prove the intended interface patterns in a small Phase A vertical slice. Fix general language semantics with regressions instead of reshaping APIs around a compiler bug.
  • DWC2 complexity: begin with EP0 and one bulk pair. FIFO sizing, reset ordering and W1C register behavior receive dedicated tests before class work.
  • Interrupt support: polling is the baseline API and correctness path. Interrupts may reduce latency later by feeding the same event queue; class code must not depend on ISR execution.
  • Memory: every function declares descriptor bytes, endpoint count, FIFO words and transfer-buffer bytes. Composite construction fails clearly when the controller budget is exceeded.
  • Interface overhead: benchmark code size and critical loops at each migration slice. Use interfaces for substitution, concrete types for ownership and hot paths.
  • Host variance: descriptor correctness is necessary but insufficient. Keep OS-specific observations in tests and documentation, not scattered conditionals in the core.
  • Shared S3 PHY: the M5StickS3 currently enumerates through the fixed USB Serial/JTAG function. DWC2 firmware must deliberately route the internal PHY to USB-OTG, so the debug serial device may disappear while a custom device is active. Preserve a recovery/flashing path and use another observable output when testing early controller bring-up.
  • API stability: mark device APIs experimental until CDC ACM, HID and vendor composite operation is proven. Stabilize the narrow interfaces before advanced class work.

Decisions required during Phase C

  1. Final package root and versioning policy for device APIs.
  2. Whether the first DWC2 driver uses FIFO-only transfers or introduces GDMA after the FIFO path is correct.
  3. Confirm the M5StickS3 USB connector exposes the S3 internal PHY path required by DWC2; use it as the qualification board once the emulator enumeration fixture passes.
  4. VID/PID policy for examples and tests; no project-wide production identifier is implied.

12. Definition of done

Issue 348 — microcontroller refactor

  • GPIO, time, buses and reusable device drivers are concrete structs satisfying documented narrow interfaces.
  • Board-attached hardware is directly usable through selectors such as board.BlueLED.Set(true); external buses are created from named connectors such as i2c.New(board.Grove).
  • M5NanoC6 and M5StickS3 examples use the shared packages and retain emulator/hardware behavior.
  • Raw chip addresses, GPIO numbers and controller selection do not leak into applications or board-agnostic drivers.
  • Temporary compatibility wrappers and duplicated board logic are removed.

Issue 347 — ESP32 USB stack

  • Portable EP0, descriptor, composite and class logic is independent of DWC2.
  • ESP32-S3 enumerates and transfers through the controller interface in emulator and on hardware.
  • The fixed ESP USB Serial/JTAG path is explicit and preserved, especially on C6.
  • Every requested class—Mass Storage, HID, CDC Ethernet, CDC ACM, MIDI, Audio, WebUSB/vendor, MTP and ADB—is implemented and validated in the same PR; none is deferred to a follow-up.
  • Public examples explain memory budgets, polling requirements, host compatibility and recovery behavior.
