Assembly files that extend a CompilerJIT backend without extending the compiler

Add .rtgasm as Renvo's project-local assembly format. Files preserve small CompilerJIT fragments as source in the canonical unit and evaluate them through VM32 against the selected target definition. Ordinary Go declarations and calls provide the program integration; target definitions provide the emitter vocabulary.

source-preserving CompilerJIT VM32 first retargetable compiler simplification

Decisions already made

RTGASM is an escape hatch, not a portable instruction language. A snippet uses the selected backend's registers, ABI, emitter methods, sequences, labels, and relocation helpers directly. Authors of handwritten assembly own those details.
Preserve source in RTGU. The frontend selects, validates ownership, and transports .rtgasm. It does not lower the fragment into a second assembly IR or merge it into a project-specific backend.
Evaluate with VM32 first. RTGASM bodies are small CompilerJIT fragments. Reuse the VM32-hosted preparation and execution path before considering a specialized evaluator. Optimize only after measuring real programs and preparation/build profiles.
The backend stays cacheable independently of projects. A prepared target artifact is keyed by the RTG definition and compiler compatibility. Project RTGASM remains program input, so editing a snippet does not rebuild the target backend.
Use the feature to remove compiler magic. Success is not merely accepting a new suffix. Suitable hardcoded byte blobs, helper emitters, name-based intrinsics, and platform fragments move beside the packages or runtime facilities that require them.

Small source shape

The syntax should be a thin top-level wrapper around the sequence language already used in RTG definitions.

Go declaration

package bits

func byteSwap64(value uint64) uint64

bits_amd64.rtgasm

rtgasm 1

assembly {
    byteSwap64(out:emitter) {
        # mov %rdi, %rax
        out.Bytes3(0x48, 0x89, 0xf8)
        # bswap %rax
        out.Bytes3(0x48, 0x0f, 0xc8)
        out.Byte(0xc3)
    }
}

A more involved fragment uses existing labels and target helpers without gaining a new control-flow language:

rtgasm 1

assembly {
    waitForReady(out:emitter) {
        let retry = out.NewLabel()
        let ready = out.NewLabel()

        out.Mark(retry)
        emitStatusLoad(out)
        jumpCondition(out, ne, ready)
        emitTargetWait(out)
        jump(out, retry)

        out.Mark(ready)
        returnInstruction(out)
    }
}
No cosmetic assembler layer. Names such as emitStatusLoad exist only if the target definition already defines them. Raw out.Byte, out.Int32, relocation methods, and target helper calls remain normal and expected.

Initial language boundary

  • Reuse RTG scanning, literals, calls, let, labels, records, and sequence statements.
  • Add only the file version and assembly-entry container needed to bind program functions.
  • No inline RTGASM in Go, macro preprocessor, portable opcode set, register allocator, or implicit prologue.
  • No embedded Go inside project RTGASM. Backend definitions may continue using their trusted generated hooks.
  • Reject unsupported syntax rather than silently compiling a Go fallback.

1. Discovery and target selection

  • Package mode discovers .rtgasm beside .go and .c.
  • Reuse Renvo's target suffix and build-constraint decisions. Examples include uart_esp32c6_riscv32.rtgasm, bios_msdos_8086.rtgasm, and syscall_pdp11.rtgasm.
  • Explicit-file mode accepts explicitly named .rtgasm files under the same-directory/package rule and preserves its existing “exact files” behavior.
  • Files selected for a non-CompilerJIT target receive a clear diagnostic unless that target later implements the same evaluator contract.

2. Ownership and linkage

  • An assembly entry binds to a bodyless function declaration in the same Go package.
  • The checker remains the authority for the Go signature and all ordinary call sites.
  • The frontend diagnoses missing declarations, duplicate Go/RTGASM bodies, duplicate assembly entries, methods not yet supported, and selected declarations with no implementation.
  • Linking resolves the entry to the function's final linked identity. The backend must not guess by an unqualified source name after package renaming.
  • Reachability follows ordinary Go calls. Unreachable RTGASM bodies are pruned before backend evaluation.

3. Canonical unit transport

Add an optional, versioned RTGU child containing a deterministic table of assembly entries. Each row stores the owning linked function index, stable source filename, metadata, and exact selected source bytes. Existing version-1 readers already skip optional child tags; nevertheless, the unit version and backend protocol must advance when the production reader begins consuming it. 

RTGASM table
  entry count
  ├── linked function index
  ├── package/import identity for diagnostics
  ├── stable relative filename
  ├── metadata flags
  └── original UTF-8 source bytes
  • Sort by linked function identity and stable filename, never filesystem enumeration order.
  • Include selected RTGASM bytes in package source identities and incremental cache invalidation.
  • Keep RTGASM outside the Go token/text stream so the existing compact parser never mistakes it for Go.
  • Preserve source locations so VM32 evaluation diagnostics name the project file and line.
  • Ensure -emit-unit output is sufficient to reproduce backend behavior without the source tree.

4. Backend insertion

  • The backend already allocates one label per linked function. For an RTGASM function, mark that label and emit the evaluated fragment instead of parsing a Go body.
  • Calls to Go and RTGASM functions use the existing function-label table and relocation machinery.
  • FunctionStart/FunctionFinish, object symbol ranges, alignment, and format bookkeeping wrap assembly entries exactly as they wrap generated functions.
  • The fragment owns its machine prologue, epilogue, register preservation, and return instruction unless metadata explicitly requests a future wrapper mode.

VM32 evaluation model

Renvo already prepares external RTG backends as native or VM32 compiler images. RTGASM should reuse that capability: compile the small fragment evaluator against the selected resolved definition, execute it in bounded VM32 state, and let it append to the current emitter.

Prepared once

The target definition and RTG sequence implementation remain in the cached CompilerJIT artifact.

Evaluated per entry

The source body and resolved function context are supplied as program data at compilation time.

Bounded execution

Instruction count, linear memory, emitted bytes, labels, and relocations receive explicit limits.

Implementation sequence

  1. Extract/reuse the RTG sequence parser and type model so an assembly body compiles through the same semantics as a definition sequence.
  2. Provide the evaluator only the selected resolved definition, an emitter capability, and the fragment source. It gets no filesystem or process capability.
  3. Compile the fragment evaluation program to vm/vm32 and execute it against the live logical emitter state.
  4. Commit emitted code, labels, relocations, symbols, data, and BSS only after successful evaluation; a failing fragment must not leave partial output.
  5. Cache parsed/compiled fragment programs by definition identity plus source digest within one build. Add persistent caching only if profiles justify it.
Do not make every project rebuild CompilerJIT. The evaluator contract belongs in the prepared backend. RTGASM source is late-bound input. A project edit should invalidate its program unit and fragment cache, not the reusable RTGB target artifact.

Complexity ladder

  1. Leaf: no arguments or one scalar argument; raw bytes; direct return.
  2. Control flow: local labels, conditional branch, bounded loop.
  3. Cross-call: RTGASM calls Go and Go calls RTGASM using normal relocations.
  4. Memory/device: pointer parameters, volatile MMIO, target-specific instruction helper.
  5. Data: local constant/table relocation or BSS reference when metadata supports it.
  6. Rooted entry: interrupt, boot, or exported object entry with no ordinary Go caller.
  7. Mixed program: multiple packages and several snippets on a constrained target.

Use RTGASM to shrink compiler magic

Migrations follow a strict rule: the new file must express the same parsed-source semantics, preserve performance/resource gates, and make ownership clearer. Do not migrate a fragment merely to advertise the feature.

Initial audit candidates

  • Large raw renvoAsmEmitText blobs in architecture and OS compiler files.
  • Lazily emitted append, string-equality, bounds-check, allocation, and memory helpers.
  • Platform argument/environment entry templates and syscall/foreign-call shims.
  • JIT-call trampolines and other runtime declarations currently recognized through special compiler paths.
  • Microcontroller startup, MMIO, cache, interrupt, and image-entry fragments.
  • DOS and PDP-11 routines that are more naturally owned beside their platform runtime packages.

Migration order

  1. Move one small, self-contained helper whose ABI and tests are already clear.
  2. Move a helper with local labels and an internal relocation.
  3. Move a helper that calls another generated or Go function.
  4. Move one microcontroller/platform fragment that demonstrates why target-local assembly matters.
  5. Audit remaining hardcoded paths and either migrate them or document why compiler ownership remains correct.
Compiler restrictions still apply. Backend implementation edits remain limited to the files allowed by AGENTS.md. RTGASM evaluation must not add filesystem or process operations to the backend compiler beyond its existing open, close, read, write, chmod, and print boundary.

Validation strategy

Frontend acceptance

  • Package and dependency discovery
  • OS/architecture suffixes and build constraints
  • Explicit file lists
  • Same-package symbol binding
  • Incremental source digest invalidation
  • -emit-unit reproducibility

Backend regressions

  • Minimal programs under backend/tests/
  • Success prints exactly PASS\n
  • Labels and relative/absolute relocations
  • Function symbols and object output
  • Malformed or over-budget fragment failure
  • No partial emission after failure

Determinism and security

  • Stable unit bytes across file enumeration order
  • Stable host and self-hosted frontend output
  • No filesystem access from fragment evaluation
  • VM instruction, memory, source, output, and relocation limits
  • No target/backend cache-key contamination by project paths

Performance

  • Zero-RTGASM projects remain near-zero overhead
  • One, many-small, and one-large fragment benchmarks
  • Prepared compiler artifact size
  • Frontend and prepared-backend peak RSS
  • Output size before and after helper migrations

Definition of done

MVP boundary Version 1 intentionally commits only final callable code bytes. Local labels and relative relocations are resolved inside the isolated evaluator. Cross-function symbolic calls, data/BSS transactions, rooted non-callable fragments, alignment overrides, and richer metadata remain follow-up features that should be added only for a concrete target use case.
  • A user adds a bodyless Go declaration and target-selected .rtgasm file; ordinary calls compile without directives or compiler source changes.
  • The canonical unit contains the exact selected RTGASM source and is sufficient for offline/repeated backend compilation.
  • A cached CompilerJIT backend evaluates fragments through bounded VM32 without being rebuilt per project.
  • Local labels, target helper calls, raw emission, and local relative relocations work.
  • Diagnostics identify project files and lines for syntax, binding, type, limit, and emission failures.
  • Representative RISC-V/ESP32, DOS/8086, PDP-11, and C89 cases are covered structurally, with DOS and PDP-11 project examples.
  • The feature adds no target-specific opcode knowledge to the frontend or shared compiler; project fragments own their target-specific emission.
  • Existing performance and resource requirements remain intact; no harness, runtime, or test is patched around missing semantics.
  • Focused tests and ./tools/check preflight pass, generated sources are current, and documentation explains the deliberately low-level ABI responsibility.
Final product test A new constrained target can define its emitter helpers, ship useful handwritten snippets in ordinary packages, and compile nontrivial programs without adding target-specific branches or byte blobs to the Renvo compiler.
